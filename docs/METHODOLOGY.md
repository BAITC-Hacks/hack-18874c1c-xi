# Методология Money Graph

## Назначение и границы вывода

Пайплайн помогает определить, какие узлы наблюдаемой сети стоит проверить первыми и какие факты это объясняют. Роль, приоритет и назначение кластера — **эвристические гипотезы для проверки**, не установленная истина, доказательство преступления или оценка виновности. Размеченных ролей нет; accuracy, precision, recall и калиброванная вероятность не заявляются.

Python — единственный источник расчётов. NestJS запускает CLI и отдаёт результат, Next.js отображает его. Форматы определены в [контрактах](CONTRACTS.md); параметры — в [config.py](../analytics/src/money_graph/config.py), формулы — в [analysis.py](../analytics/src/money_graph/analysis.py). Этот документ не заменяет приёмочные тесты и измерение полного времени запуска.

## 1. Входы, точность и профиль набора

Источники — три Parquet и [описание организаторов](references/organizers/DATASET.md). `nodes.parquet` задаёт полный перечень узлов; `edges.parquet` — направленные агрегаты `src → dst`; `transactions.parquet` — те же операции по отдельности. Оборот из рёбер и транзакций нельзя складывать: это два представления одного потока.

Профилирование предоставленных файлов показало следующее. Это описание конкретного входа, а не зашитые в алгоритм размеры, ожидаемые роли или доказательство приёмки готового продукта.

Квантили приводятся с линейной интерполяцией и не пересчитывают пороги автоматически при каждом запуске.

### Проверка входов

До анализа проверяются обязательные поля и типы, отсутствие null, уникальность gid и направленных пар рёбер, допустимые глубины и их согласованность, ссылки на известные узлы, положительность сумм и числа транзакций. По каждой паре `src/dst` сумма и количество строк transactions должны точно совпасть с `sum_kzt` и `n_tx` из edges. Несогласованный набор отклоняется, а не исправляется предположениями.

Все gid сохраняются как int64; в JSON они являются строками. Для данного набора все gid выходят за безопасный целочисленный диапазон JavaScript Number. Текстовые идентификаторы нельзя преобразовывать в Number или сортировать лексикографически там, где требуется числовой порядок.

Денежное значение на входе преобразуется через `Decimal(str(value))` в целое число тиынов: `amount_minor = amount_KZT × 100`. Дроби точнее тиына отклоняются без округления. Финансовые агрегаты считаются целыми числами, а в выходах записываются в KZT с двумя десятичными знаками; в JSON — строками. Это сохраняет десятичное представление переданного float64, но не восстанавливает точность, если она была потеряна до создания исходного файла. Float используется для безразмерного ratio и оценок, не для накопления денежных сумм.

## 2. Метрики узла

Обозначения: `I = in_degree`, `O = out_degree`, `S_in = in_sum_kzt`, `S_out = out_sum_kzt`, `R = out_in_ratio`. Все величины относятся только к наблюдаемой выборке.

| Поле `nodes[].metrics` | Определение |
| :--- | :--- |
| `in_degree` | Число уникальных отправителей: количество направленных агрегированных рёбер, заканчивающихся в узле |
| `out_degree` | Число уникальных получателей: количество направленных агрегированных рёбер, начинающихся в узле |
| `in_sum_kzt` | Точная сумма входящих рёбер |
| `out_sum_kzt` | Точная сумма исходящих рёбер |
| `n_tx_in` | Сумма `n_tx` входящих рёбер |
| `n_tx_out` | Сумма `n_tx` исходящих рёбер |
| `out_in_ratio` | `S_out / S_in`, если `S_in > 0`; иначе `null` |

Встречный контрагент учитывается отдельно во входящей и исходящей степенях. Если во входе есть самоперевод, он учитывается один раз в каждой направленной степени и сумме. `I + O` не обязательно равно числу уникальных соседей. `S_in + S_out` — объём активности отдельного узла, **не остаток на счёте и не оборот всей сети**. Суммирование этой величины по узлам дважды учитывает каждое ребро.

Для coordinator дополнительно вычисляется внутренний признак `E`: количество различных кластеров непосредственных соседей узла, кроме его собственного кластера. Учитываются и отправители, и получатели; каждый внешний кластер — один раз. `E` приводится в evidence coordinator, но не добавляется восьмым полем в контрактный объект `metrics`.

## 3. Кластеризация

Используется Louvain из закреплённой версии NetworkX, без SciPy, отдельного сервиса или обучения. Louvain — эвристика оптимизации модульности; порядок узлов и параметр разрешения могут менять результат. Особое обращение с самопетлями также описано в [официальной документации NetworkX](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.community.louvain.louvain_communities.html).

Преобразование и порядок действий:

1. Добавить все узлы из nodes в направленный граф; рёбра упорядочить по числовым `(src, dst)`.
2. Создать неориентированную проекцию для кластеризации со всеми узлами. Вес пары `{u,v}` — сумма направленных сумм `u→v` и `v→u` в целых тиынах. Отсутствующее направление даёт ноль.
3. Самопереводы исключить **только из проекции кластеризации**: они не должны интерпретироваться как ранее объединённые сообщества. В исходном графе, денежных метриках и экспортах они остаются.
4. Обрабатывать каждую связную компоненту проекции отдельно; порядок компонент — по минимальному числовому gid. Узлы внутри неё добавлять в числовом порядке. Это локальная кластеризация по компонентам, а не одна оптимизация модульности на объединённой сети.
5. Для компоненты с рёбрами вызвать Louvain: `weight="weight"`, `seed=42`, `resolution=1.0`, `threshold=1e-7`; ограничение числа уровней отдельно не задаётся. Каждый изолированный узел образует собственный кластер.
6. Разделить каждый возвращённый кластер на связные части его индуцированного подграфа, если таких частей несколько. Это не позволяет одному итоговому кластеру объединять несвязанные части.
7. Отсортировать итоговые группы по `(-число_узлов, минимальный_числовой_gid)` и присвоить целые `cluster_id` с **0**.

Число кластеров не фиксируется заранее. Восемь сообществ с несколькими seeds из описания организаторов — справочное наблюдение, не целевой параметр. Кластер не доказывает общую цель или управление: близость может отражать сильные суммы отдельных переводов, структуру выгрузки и особенности выбранного разрешения.

`sum_kzt_internal` считается заново по исходным направленным рёбрам, у которых оба конца принадлежат кластеру. Каждое ребро учитывается один раз, включая допустимый самоперевод. Нельзя использовать сумму степеней проекции как внутренний оборот. Межкластерные переводы в этот показатель не входят; поэтому сумма внутренних оборотов всех кластеров может быть меньше общего оборота.

`n_nodes` и `n_seed` — фактические количества узлов и seeds. `top_gids` содержит до трёх узлов кластера с наибольшим итоговым priority_score; при равенстве используется числовой gid по возрастанию. `hypothesis` описывает размер, seeds, наблюдаемые признаки ролей и внутренний оборот с оговоркой о недоказанной общей цели. Для изолята прямо указывается недостаточность наблюдаемых связей.

## 4. Одна роль на узел

Правила проверяются **сверху вниз**. Побеждает первое выполненное правило; остальные не создают дополнительные роли. Поэтому число узлов с отдельным признаком может быть больше числа назначений соответствующей роли. `depth < 4` обозначает внутреннюю часть исходящего обхода, но не полноту всех банковских операций.

| Приоритет | Роль | Формальное правило при стандартных параметрах | Смысл и ограничение |
| :--- | :--- | :--- | :--- |
| 1 | `coordinator` | `I ≥ 5` и `O ≥ 5` и `E ≥ 2` | Двухсторонний узел с несколькими внешними сообществами; гипотеза связующей позиции, не доказательство организационного контроля |
| 2 | `consolidator` | `I ≥ 3` и `I ≥ 2 × O` | Концентрация наблюдаемых входящих связей; не доказательство удержания средств |
| 3 | `distributor` | `O ≥ 5` и `O ≥ 2 × I` | Выраженное распределение по исходящим связям; внешние входящие источники могут быть неизвестны |
| 4 | `transit` | Не seed, `depth < 4`, `S_in > 0`, `S_out > 0`, `0.8 ≤ R ≤ 1.2` | Сходные месячные суммы входа и выхода; скорость и порядок прохождения денег неизвестны |
| 5 | `terminal` | Не seed, `depth < 4`, `I > 0`, `O = 0` | Конечный получатель только в наблюдаемом фрагменте; остаток на счёте неизвестен |
| 6 | `peripheral` | Ни одно предыдущее правило не выполнено | Недостаточно признаков выбранных правил; это не подтверждение низкого риска или непричастности |

Seed-статус сам по себе не повышает роль или приоритет. Seeds могут соответствовать структурным правилам coordinator/consolidator/distributor, но для них не применяется ratio-правило transit и не назначается terminal. Ratio при ненулевом знаменателе всё равно отображается как наблюдаемая метрика с предупреждением.

На depth=4 нельзя назначать terminal по отсутствию исходящих переводов. Вместе с тем большое число видимых отправителей остаётся наблюдаемым фактом: такой узел может получить consolidator, но evidence и limitations отмечают границу обхода. Правило не утверждает, что собранные деньги остались у него. Изоляты получают peripheral, нулевой role_score и собственный кластер.

### Role score

`role_score` — выраженность признаков выбранного правила, а не вероятность правильной классификации. Оценки разных ролей заданы одной прозрачной политикой, но не калиброваны на одинаковую эмпирическую вероятность. Пороговое назначение роли и непрерывный score выполняют разные задачи.

Для стандартных параметров `mean` — обычное среднее аргументов:

```text
coordinator:  0.45 + 0.45 × mean(min(I/10, 1), min(O/10, 1), min(E/4, 1))
consolidator: 0.40 + 0.50 × mean(min(I/6, 1), 1 - O/I)
distributor:  0.40 + 0.50 × mean(min(O/10, 1), 1 - I/O)
transit:      0.35 + 0.30 × max(0, 1 - abs(R - 1)/0.20)
terminal:     0.35 + 0.25 × min(I/3, 1)
peripheral:   0.10 при I + O > 0; иначе 0
```

Деления безопасны благодаря предварительно выполненным условиям соответствующей роли. Для transit максимум соответствует `R=1`, минимум — краям допустимого диапазона. Отсутствие исходящих у terminal не создаёт уверенность 1. Для координатора и двух fan-правил верхняя граница score равна 0,90.

При изменении конфигурации знаменатели структурных score составляют удвоенные пороги соответствующих правил: `2×coordinator_in`, `2×coordinator_out`, `2×coordinator_external_clusters`, `2×consolidator_in`, `2×distributor_out`. У terminal знаменатель равен `consolidator_in`. Допуск transit ниже 1 равен `1-transit_ratio_low`, выше 1 — `transit_ratio_high-1`. Коэффициенты 0,45/0,40/0,50/0,35/0,30/0,25 остаются частью формул, а не обучаемыми параметрами. Смена порогов — изменение методологии, требующее проверки и документации.

## 5. Приоритет проверки и объяснения

Приоритет ориентирован на задачу поиска точек концентрации: разнообразие отправителей получает больший вес, чем fan-out. Объём учитывает масштаб наблюдаемой активности; role_score — выраженность классификационных признаков. Весов для seed, заранее выбранного gid или квот для ролей нет.

Для каждого узла `V = S_in + S_out` **в KZT**. Максимумы берутся по всем узлам текущего входа:

```text
N(x) = log(1 + x) / log(1 + max(x))
N(x) = 0, если max(x) = 0

priority_score = 0.35 × N(V)
               + 0.35 × N(I)
               + 0.10 × N(O)
               + 0.20 × role_score
```

У `N(V)`, `N(I)` и `N(O)` собственные максимумы. Логарифм уменьшает доминирование единичного крупного значения; максимальная нормировка делает score относительным текущему набору. Одинаковый узел в изменённой выборке может получить другой приоритет: это не абсолютная оценка риска.

Единица V существенна: `log(1+x)` не инвариантен переходу KZT → тиыны. В коде используется эквивалентная форма `(log(100+V_minor)-log(100)) / (log(100+max(V_minor))-log(100))`, где точные денежные агрегаты остаются целыми тиынами. Вещественная аппроксимация нужна только при вычислении нормированной оценки, а не денежных итогов.

Role_score округляется до шести знаков перед использованием в приоритете; итоговый priority_score — до шести знаков. Сортировка производится по опубликованному priority_score убывающе, при равенстве — по числовому gid возрастающе. `top_nodes.csv` содержит первые 20 узлов; если узлов меньше 20, все узлы. `rank` начинается с 1. Политика top-3 внутри кластеров использует тот же порядок.

`evidence` объясняет именно роль через реальные значения и сработавшее правило, не превышает 200 Unicode-символов. `why` объясняет приоритет: показывает нормированные слагаемые и их веса, наблюдаемые величины и ограничение выборки. `limitations` хранит ограничения узла отдельно. Эти объяснения основаны на вычисленных данных, не на текстовых догадках; произвольный gid можно разобрать теми же правилами, даже если он не попал в топ.

## 7. Ограничения и корректная интерпретация

- Выгрузка содержит только внутрибанковские исходящие обходы от seeds за июль 2026 года; другие банки, периоды и внешние входящие источники неизвестны.
- Переводы менее 5 000 KZT отсутствуют. Нельзя делать выводы о дроблении сумм ниже этого порога или полном количестве операций клиента.
- На глубине 4 обход остановлен. Отсутствие дальнейших переводов не означает удержание денег. Граница не удаляется из анализа и не заменяется искусственными рёбрами.
- Входящие особенно неполны у seeds, но ограничение касается всей выборки. `R>1` сам по себе не является аномалией или ошибкой. Нулевой наблюдаемый вход — не доказательство отсутствия реального источника средств.
- Равенство месячных входа и выхода не устанавливает, что отправлены именно полученные средства, и не измеряет скорость транзита. Временные паттерны в базовом методе не анализируются.
- Высокая степень, объём или межкластерная связь возможны у разных типов участников. Атрибутов клиентов и ground truth нет; организационный контроль из этой структуры не устанавливается.
- Louvain и связанные с ним признаки чувствительны к весам, разрешению и неполноте наблюдений. Финансовые агрегаты от кластеризации не меняются; роль coordinator может измениться при другом разбиении.
- Экстремальные суммы могут превысить численный диапазон внутренних вычислений Louvain. В таком случае CLI завершает расчёт понятной ошибкой входов без публикации результата; точные финансовые суммы не обрезаются и не округляются ради успешного запуска.
- Изоляты остаются доступными для поиска; их нулевой приоритет означает отсутствие структурных признаков в файлах, не отсутствие интереса к ним вне этого анализа.
- Данные предоставлены для хакатона. В репозиторий не добавляются исходные Parquet, реальные индивидуальные примеры gid или производные списки клиентов без отдельного разрешения. Локальные материалы демо хранятся отдельно от публикуемой методологии.

## 8. Воспроизводимость и проверка

Используются закреплённые зависимости, числовая сортировка входных записей, детерминированный порядок добавления узлов/рёбер, seed Louvain и стабильная нумерация кластеров. Повторяемость относится к одному набору, версии кода, настройкам и окружению. Номер кластера не является постоянным идентификатором между изменениями данных: изменение размера группы может перенумеровать и другие кластеры.

Сравнение повторных запусков исключает `metadata.elapsed_ms`, но должно сохранять роли, оценки, кластеры, порядок рейтинга, evidence и финансовые итоги. Перестановка строк исходных файлов не должна менять аналитический результат. Проверки должны отдельно покрывать изолят, seed-получателя, depth=4, нулевой знаменатель, конфликт правил, точность денег и gid, одинаковый приоритет и несовместимые входы.

Успешный CLI создаёт три обязательных CSV и согласованный `analysis.json`; отсутствие ошибок импорта или наличие файлов само по себе не доказывает их корректность. Полнота проверяется сравнением множества выходных gid с nodes, а не только ожидаемым числом строк. Сумма размеров кластеров должна равняться числу узлов, сумма seeds — числу исходных seeds. Денежные проверки выполняются точно, без float-допуска.

`metadata.elapsed_ms` измеряет аналитическую часть до сериализации выходных файлов. Для требования ТЗ **полный процесс** измеряется снаружи: от запуска CLI с исходными Parquet до успешного завершения записи и проверки артефактов, включая сериализацию. Это отдельный замер wall-clock; время установки зависимостей и сборки не подменяет время расчёта. Фактические команды, результаты тестов и измерения фиксируются в инструкции запуска/отчёте проверки, а не выводятся из данного описания алгоритма.

## 9. Что изменить для графа около миллиона узлов

Это направление развития, не реализованная распределённая система и не обещание сохранения текущего времени расчёта.

1. Считать и валидировать Parquet пакетами; группировать транзакции с контролем памяти. Хранить денежные агрегаты в точных целочисленных/decimal типах с проверкой диапазона, а не переносить их в float ради скорости.
2. Заменить объектный граф Python/NetworkX компактным представлением смежности и эффективной реализацией кластеризации после измерения профиля памяти и времени. Простые локальные метрики и правила остаются линейными по проходу рёбер; стоимость Louvain нужно измерять отдельно, особенно для гигантской компоненты.
3. Независимые компоненты обрабатывать параллельно с детерминированными входами и последующей стабильной нумерацией. Одну огромную компоненту нельзя произвольно разрезать без оценки изменения сообществ и coordinator-признаков.
4. Не материализовывать весь JSON и весь граф в браузере. API потребуется выдавать индексированные карточки, топ, агрегаты кластеров и ограниченные окрестности; поиск должен сохранять доступность каждого gid, включая изоляты.
5. Отдельно пересмотреть пороги и относительную нормировку на новом распределении, сравнить устойчивость сообществ и ранжирования. Не переносить сегодняшние численные score как абсолютный риск и не объявлять масштабирование доказанным без воспроизводимого теста.

Ни БД, ни брокер, ни дополнительный Python HTTP API не требуются для текущего объёма и не добавляются только ради этого раздела.
