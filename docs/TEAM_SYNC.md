# Синхронизация команды каждые 20 минут

Правило владельца проекта от 23.09.2026: каждые 20 минут сохранять проверенные собственные изменения, получать обновления коллег, объединять их **в свою ветку** и отправлять свою ветку в `origin`. Оно действует до отмены пользователем и не разрешает деплой, публикацию данных, изменение чужих веток или `main`.

## Один цикл

1. Проверить корень репозитория, `origin` (`BAITC-Hacks/hack-18874c1c-xi`), имя текущей ветки, `git status` и `npm run team:check`. Использовать имя, уже явно подтверждённое в этой задаче; на каждом срабатывании не спрашивать его снова. Если checkout сменился, есть незавершённый merge/rebase или другой процесс меняет те же файлы — остановить цикл без переключения веток и изменений Git.
2. Просмотреть diff и index. Если в index уже есть чужие или неясные staged-изменения — остановиться до любых add/commit, не сбрасывать их. В коммит включать явными путями только законченные изменения этой задачи, прошедшие релевантные тесты; перед commit проверить весь staged diff, а не только последние добавленные пути. Не использовать слепой `git add .`/`git add -A`, не захватывать чужие staged/unstaged изменения, секреты, `.env`, IDE-файлы, `data/`, `runs/`, `artifacts/`. Незаконченные или непроверенные изменения не публиковать ради таймера.
3. Если есть собственные готовые изменения — сделать содержательный коммит. При неизвестных или незаконченных tracked-изменениях оставить их нетронутыми и не делать merge. Изолированные untracked-файлы, например `.idea/`, можно оставить, если входящие ветки не затронут их пути. При сомнении остановиться, без автоматического stash.
4. Выполнить `git fetch origin`. Просмотреть новые коммиты и изменённые пути. Сначала объединить `origin/<своя-ветка>` со своей локальной веткой, затем по очереди две ветки коллег из таблицы. Использовать обычный `git merge --no-edit origin/<ветка>` (fast-forward, если возможен), без rebase и без переписывания опубликованной истории. Уже включённые изменения не требуют нового коммита.
5. При конфликте, неожиданной смене структуры/контракта, подозрительных файлах или расхождении требований остановить автоматическое слияние и сообщить конкретные файлы/причину. Не выбирать целую сторону `ours/theirs`, не удалять работу и не обходить hooks. Дальнейшее разрешение конфликта требует отдельного решения пользователя; текущий явно порученный ручной merge можно разрешать по проверенным фактам.
6. Проверить итог: `npm run team:check`, `npm run check:structure`, `git diff --check`, тесты и типы изменённых компонентов. При объединении API и аналитики — `npm test`, `npm run typecheck`, Python-тесты и `test:python`; при доступных настоящих данных — `test:dataset`. При изменении сборки, зависимостей или стыков компонентов — сборка и Docker Compose. Команды установки и проверки находятся в README. Не подменять отсутствующие данные fixture и не называть непроведённую проверку успешной. Блокирующая ошибка означает **не пушить**; таймер сам по себе не поручает разработку новых функций или широкие исправления чужого кода.
7. Перед отправкой ещё раз проверить ветку, статус и состав исходящих коммитов. Выполнить только `git push origin <своя-ветка>:<своя-ветка>`, без `--force`, `--all`, tags и push в `main`. После отправки проверить соответствие локального HEAD удалённой своей ветке. Если push отклонён из-за новых коммитов или доступа — завершить цикл, не делать бесконечных повторов и не обходить ограничения.

Один цикл — не более одного fetch и одной попытки merge каждого источника. Если новых изменений нет, не создавать пустых коммитов и не делать повторные сборки неизменённого уже проверенного HEAD. Сообщать о содержательной синхронизации (ветки/commit, проверки), ошибке или необходимом решении; не присылать повторные сообщения о неизменном состоянии. «Остановить цикл» означает прекратить Git-изменения текущего запуска, не отменять расписание: следующие срабатывания только проверяют, устранён ли блокер, и не продолжают незавершённое слияние без решения пользователя. Отключать расписание по просьбе пользователя.

## Настройка расписания

В Codex Desktop настройка выполняется настоящей повторяющейся задачей **в текущем чате**, каждые 20 минут. Сначала проверить, нет ли уже такого расписания, и обновить существующее вместо создания дубликата. У каждого участника — один таймер и отдельный клон/worktree. Дочерние агенты не создают таймеры и не выполняют Git-синхронизацию общего checkout.

В расписании сохранить имя участника, абсолютный путь его клона, точную свою ветку, две ветки-источника и ссылку на этот протокол. Имя и путь нельзя угадывать. Если инструмент расписания недоступен, честно сообщить, что таймер **не создан**; текст skill/промпта и hooks сами ничего по времени не запускают. Не заменять таймер shell-циклом или cron без отдельного запроса.

Для задач с локальными файлами компьютер должен быть включён, приложение — запущено, репозиторий — доступен. Интервал задаёт расписание проверок, а не обещание безусловного push ровно по минутам: безопасность, тесты, доступность и незавершённая работа имеют приоритет. Основание: [официальная документация расписаний](https://learn.chatgpt.com/docs/automations?surface=app).
