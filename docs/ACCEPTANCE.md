# Приёмочный стенд: пять must-have

Стенд проверяет настоящий путь Parquet → Python CLI → NestJS → production Next.js → Chromium → скачанные CSV. AI, моки API и dev-fixture в этом прогоне не используются. Автоматический успех не является оценкой жюри или подтверждением качества выявления отмывания.

**Это необязательный инструмент команды, не команда запуска для жюри.** Обычный `docker compose up --build --wait` и прямой запуск CLI из README не собирают тестовые стадии, не устанавливают Chromium и не выполняют эти тесты. Файлы тестов сохраняются в репозитории для воспроизводимой проверки качества; после прогона их контейнеры останавливаются. Browser image остаётся только в локальном Docker-кэше, не внутри API/web/analytics.

API получает отдельное production-дерево зависимостей после `npm prune --omit=dev --omit=optional`; проверка внутри его Docker-сборки запрещает Playwright, TypeScript и tsx. Полный набор npm-инструментов остаётся только в стадиях сборки/проверки, а готовый web поставляется как Next.js standalone. Удаление тестов из Git не требуется и не ускоряет обычный запуск.

## Одна команда

Предварительные условия: Git, Node.js 24 LTS и работающий Docker Engine/Desktop с Docker Compose v2 (`--wait`). Получить исходные три Parquet организаторов отдельно и положить в `data/`. Нужны доступ к реестрам образов/npm/PyPI при первой сборке и свободное место для браузерного образа. Датасет не публикуется в Git.

Из корня клона, без установки npm/Python/Chromium на хосте:

```sh
node scripts/acceptance/run.mjs --no-cache
```

После обычного `npm ci` эквивалентная команда:

```sh
npm run test:acceptance -- --no-cache
```

`--no-cache` заново выполняет установку зависимостей и сборку Docker-слоёв. Без флага используются доступные build-cache слои, но CLI каждый раз читает исходные Parquet и создаёт новые результаты. Оба запуска CLI и каждый API-запуск пересчитывают данные; старые результаты не используются как новый расчёт. Установка и сборка измеряются отдельно от лимита 300 секунд.

Браузерный контейнер собирается на закреплённом Node-образе: Playwright 1.63.0 из общего lockfile устанавливает только соответствующий ему Chromium и системные зависимости. Это [поддерживаемый способ собственной Docker-сборки](https://playwright.dev/docs/docker#build-your-own-image); большой готовый multi-browser образ не требуется. Debian-пакеты берутся из репозиториев при сборке, поэтому побайтовая идентичность образов не обещается.

Другой каталог данных:

```sh
node scripts/acceptance/run.mjs --data-dir "/absolute/path/to/data" --no-cache
```

Отсутствующий/пустой файл означает ошибку, не пропуск и не переключение на синтетику. Приёмочный режим проверяет именно выданный набор (2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81 seed); алгоритм продукта по-прежнему не привязан к этим размерам.

## Изоляция и отчёты

- Каждый запуск создаёт отдельный Docker Compose project `mg-acceptance-…`. Порты хоста не публикуются; существующий `docker compose up` на 3000/3001 не затрагивается.
- Используются те же production-цели Dockerfile `api`, `web` и та же аналитика. Отличия стенда: внутренние адреса `http://web:3000`/`http://api:3001/api`, отдельный каталог запусков и проверочные контейнеры.
- Исходные Parquet подключены read-only. Контейнеры тестов работают во внутренней сети Docker без внешнего runtime-доступа; установка образов/зависимостей происходит до этого.
- Результаты сохраняются только в `artifacts/acceptance-<unique>/`: итоговый `report.json`, `pipeline.json`, оба CLI-результата, браузерные отчёты/скриншоты, загрузки CSV и диагностические логи. Папка исключена из Git.
- Скриншоты, traces, CSV и отчёты могут содержать реальные gid и данные переводов. Не прикреплять их к публичным CI/PR и не отправлять моделям без отдельного разрешения.
- В конце runner останавливает только собственный уникальный project, в том числе после ошибки. Он не удаляет локальные отчёты, рабочие `runs/`, данные или контейнеры других проектов.
- Exit code 0 означает `automated_pass_manual_pending`; ненулевой — ошибка. `report.json` указывает упавший этап и соответствующий файл в `logs/`. Если остановка Docker не удалась, отчёт содержит команду для конкретного проекта; не применять `docker system prune` для очистки стенда.

## Матрица обязательных требований

| Must-have | Автоматическое доказательство | Что проверяет человек |
| :--- | :--- | :--- |
| M1. Один запуск Parquet → 3 CSV, <300 с | Два свежих вызова штатного CLI с внешним таймером, точные заголовки/содержимое, побайтовая повторяемость CSV. Реальный HTTP-запуск тем же CLI. Полная контейнерная сборка; `--no-cache` исключает готовые build-слои | Другой участник повторяет команды README на отдельной машине/чистом клоне. Контейнерный прогон на машине автора не выдаётся за такую проверку |
| M2. Роль/score/evidence всех 2 248 узлов | Сравнение **множества** gid с сырым nodes.parquet, без потерь/лишних/дубликатов; словарь ролей, конечные scores [0,1], непустое evidence ≤200 символов; совпадение CSV/JSON/API | Убедиться, что формулировки понятны и не содержат необоснованных обвинений |
| M3. Формальные объяснимые правила | Независимый тестовый oracle пересчитывает документированные правила/порядок/score из исходных данных; проверяет карточки трёх выбранных gid, точные метрики, evidence и ограничения. Наличие документов — проверяемый минимум, не доказательство качества текста | Жюри/коллега выбирает три произвольных gid; команда за **одну минуту на все три** объясняет метрики, правило, приоритет и ограничения. Автоматический поиск за минуту не равен устному объяснению |
| M4. Кластеры и статистика | Полное покрытие узлов, размеры, seeds, точный внутренний оборот по исходным направленным рёбрам без двойного учёта, представители и гипотезы; согласованность карты/карточки | Оценить содержательность осторожных гипотез: кластер не доказывает общий контроль |
| M5. Топ ≥20 + карта + поиск | Ранги/порядок/why, целостность 2 248 узлов и 3 119 направленных рёбер в Cytoscape, легенда/кластеры, поиск изолята, seed-получателя, depth=4 и узла вне топа; связи и точные gid; UI-скачивание трёх CSV с повторной независимой сверкой | Проверить читаемость стрелок и интерфейса на целевом экране, выполнить живое пятиминутное демо |

Oracle — отдельный тестовый код, он не вызывается приложением и не дублирует бизнес-логику в NestJS/Next.js. Он намеренно не использует production `classify`/`validate_snapshot` как источник ожидаемого результата. Контрпримеры проверяют, что согласованное искажение CSV+JSON не проходит проверку только благодаря самосогласованности.

Границы независимого oracle: даты транзакций проверяются тестами входного валидатора продукта, но не пересчитываются этим модулем; для кластеров независимо проверяются покрытие, связность и агрегаты, а не повторная реализация конкретной конфигурации Louvain или оптимальность разбиения.

Негативные проверки: неполная загрузка, повреждённый Parquet, отсутствие результатов при failed, неизвестные запуски/экспорты, освобождение слота и повторный запуск, отсутствие старого результата на экране. Детерминированные unit/integration-тесты backend дополнительно покрывают одновременный запуск, timeout, недостающие/испорченные артефакты и завершение процесса; браузерные тесты не имитируют эти ошибки ответами-заглушками.

| Техническая реализация | 25 | Python — один источник расчётов, строгие контракты, точные деньги/gid, регрессии, CLI/API/UI, воспроизводимость | Оценка архитектурных компромиссов. AI не обязателен и не заявляется внедрённым |

Стенд **не присваивает баллы из 100**. Он сохраняет доказательства и отдельно оставляет ручные пункты `pending`.

## Ручная финальная приёмка

1. Другой участник получает новый клон и официальные данные, выполняет команды без подсказок автора, записывает commit, ОС, время сборки и расчёта.
2. Выбирает три gid сам (не только заранее подготовленные примеры). Секундомер на 60 секунд: найти каждый узел → объяснить численные признаки и правило → назвать ограничение. Отдельно различить role_score и priority_score.
3. Проверяет изолят, входящий-only seed и depth=4. Никаких выводов о виновности/остатках/полноте денежных потоков из отсутствия рёбер.
4. Проверяет стрелки, связь строки топа с картой, соответствие карточки CSV и читаемость на фактическом экране презентации.
5. Проводит пятиминутную репетицию от запуска до выгрузок и 2–3 разобранных узлов; комплект передачи данных согласуется отдельно.

CI без исходного датасета выполняет синтетические unit/regression-тесты и тесты самого oracle. Такой зелёный CI не заменяет локальный официальный end-to-end. Не загружать организаторские данные в GitHub для автоматизации приёмки.
