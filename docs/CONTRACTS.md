# Money Graph — контракты интеграции v1

Это проектное решение команды для параллельной реализации Next.js, NestJS и Python CLI. Оно не добавляет продуктовых требований к ТЗ. **API, аналитический CLI и интерфейс объединены по v1; результаты приёмки указаны в README.** Python создаёт три CSV и JSON, NestJS публикует только проверенные результаты. Команды — в README и [инструкции аналитики](../analytics/README.md). Поля и схемы аналитического контракта не изменены. Служебный `GET /api/health` возвращает `200` и `{ "status": "ok", "service": "api" }`: это только доступность HTTP. Устаревшее поле `analytics` удалено из ответа и общего типа; frontend его не использует. Готовность конкретного результата подтверждается статусом `completed` после процесса CLI и проверки артефактов, а не health.

Ерасыл координирует контракт; аналитик отвечает за значения и выходные файлы; Илья — за потребление результатов. Изменения согласованно вносятся в производителей и потребителей.

## 1. Расположение и установка

- `apps/web/` — Next.js + TypeScript + Cytoscape.js.
- `apps/api/` — NestJS + TypeScript, единственный HTTP API.
- `analytics/` — устанавливаемый Python-пакет `money_graph` и тесты аналитики.
- `packages/contracts/` — общие TypeScript-типы для приложений и `analysis.schema.json` для проверки формы результата. Семантические проверки полноты, int64-диапазона и согласованности остаются обязательными сверх JSON Schema.
- `data/` — исходные данные при прямом CLI-запуске, если предоставлены организаторами.
- `runs/<run_id>/input/` и `runs/<run_id>/output/` — локальные каталоги запусков API; идентификатор и пути создаёт сервер.

Базовые runtime: Node.js 24 LTS, Python 3.12. npm и Python-зависимости закреплены lock-файлами; рабочая команда запуска каркаса — `docker compose up --build --wait`. Установка, разработка и независимый CLI описаны в README. Смена верхнего уровня структуры и стека требует решения владельца проекта. Удалённые CDN, API-ключи и платные сервисы не нужны для обязательного сценария.

## 2. Python CLI

После установки пакета команду можно выполнять из корня репозитория:

```text
python -m money_graph --input-dir <directory> --output-dir <directory>
```

Во входном каталоге ожидаются `nodes.parquet`, `edges.parquet`, `transactions.parquet`. Точная схема берётся из README датасета. CLI читает реальные файлы при каждом полном запуске; не подменяет расчёт кешем предыдущих результатов.

Успешный запуск создаёт:

1. `nodes_roles.csv`;
2. `clusters.csv`;
3. `top_nodes.csv`;
4. `analysis.json` — внутреннее представление того же результата для API и экрана.

Exit code `0` — все файлы созданы и проверены; ненулевой — ошибка. Диагностика должна быть понятна человеку; stderr предназначен для ошибок. HTTP API не разбирает произвольный текст логов как данные, а читает проверенный `analysis.json` после успешного завершения. Измеряется фактическое время расчёта; целевой полный запуск со всеми артефактами также укладывается в 300 секунд.

Результат создаётся в отдельном каталоге запуска. Статус `completed` публикуется только после успешного процесса и проверки всех файлов; частично записанные файлы не доступны пользователю. Аналитические алгоритмы не зависят от NestJS или Next.js.

## 3. Обязательные CSV — схемы из ТЗ

Кодировка UTF-8, стандартное CSV-экранирование, первая строка — названия столбцов в указанном порядке. Дополнительные метрики сохраняются в JSON, а не добавляются в обязательные схемы CSV.

### nodes_roles.csv

```text
gid,role,role_score,cluster_id,priority_score,evidence
```

- `gid`: точное десятичное представление int64, без дробной части или потери разрядов.
- `role`: одно из `consolidator`, `transit`, `distributor`, `terminal`, `coordinator`, `peripheral`.
- `role_score`, `priority_score`: конечные числа в диапазоне [0, 1]. Это разные показатели; их смысл и формулы документирует аналитик.
- `cluster_id`: целое число, соответствующее строке clusters.csv.
- `evidence`: непустая понятная строка до 200 Unicode-символов, основанная на метриках и ограничениях данного узла.

Ровно одна строка на каждый уникальный gid из nodes.parquet. Для официального набора ожидается 2 248 строк. Ни изоляты, ни seeds без исходящих не удаляются.

### clusters.csv

```text
cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis
```

Одна строка на кластер; счётчики — целые числа. `sum_kzt_internal` — сумма наблюдаемых переводов с обоими концами внутри кластера, каждый перевод учитывается один раз. Рёбра и транзакции не суммируются друг с другом как независимые обороты.

`top_gids` сериализуется как JSON-массив строковых gid внутри CSV-поля со стандартным экранированием. Состав и число представителей определяются документированной политикой аналитика, одинаковой для всех кластеров; gid принадлежат своему кластеру. `hypothesis` — непустая осторожная гипотеза на основе фактов, включая допустимое указание на недостаточность связей у изолята.

### top_nodes.csv

```text
rank,gid,role,priority_score,why
```

Не менее 20 уникальных узлов официального набора; `rank` последовательно от 1. Сортировка — `priority_score` по убыванию, при равенстве числовой `gid` по возрастанию. `role` и `priority_score` совпадают с nodes_roles.csv; `why` — непустое объяснение именно приоритета. Ограничение в 200 символов относится к evidence, а не к why.

Для небольших синтетических тестовых графов разрешён топ из всех узлов, если их меньше 20; это не ослабляет требование официального датасета.

## 4. Внутренний analysis.json

Снимок имеет обязательные верхнеуровневые поля `metadata`, `nodes`, `edges`, `clusters`, `top_nodes`. Он генерируется из тех же итоговых таблиц, что и CSV.

### Общие типы

- Все `gid`, `src`, `dst` и элементы `top_gids` — десятичные строки, сохраняющие точный int64. JavaScript не преобразует идентификаторы в Number.
- Все денежные суммы, включая `sum_kzt`, `in_sum_kzt`, `out_sum_kzt` и `sum_kzt_internal`, — десятичные строки без разделителей тысяч; единица измерения — KZT. В Python исходная точность сохраняется: целые суммы или точная десятичная арифметика по схеме датасета. В CSV суммы также записываются точно, без локализованного форматирования.
- `cluster_id`, `rank`, `depth` и счётчики — целые JSON-числа, `is_seed` — boolean.
- Оценки — конечные JSON-числа в [0, 1]; `NaN` и Infinity запрещены.
- Для неопределённого отношения используется `null` и пояснение, а не выдуманный ноль. При UI-форматировании суммы не переагрегируются; расчёты остаются в Python.

### Поля снимка

| Объект | Поля |
| :--- | :--- |
| `metadata` | `schema_version: "1.0"`, `n_nodes`, `n_edges`, `n_transactions`, `n_seeds`, `elapsed_ms`, `warnings: string[]` |
| Элемент `nodes` | Поля nodes_roles.csv плюс `depth`, `is_seed`, `metrics`, `limitations: string[]` |
| `nodes[].metrics` | `in_degree`, `out_degree`, `in_sum_kzt`, `out_sum_kzt`, `n_tx_in`, `n_tx_out`, `out_in_ratio` |
| Элемент `edges` | `src`, `dst`, `sum_kzt`, `n_tx`, `depth` из проверенного набора агрегированных направленных рёбер |
| Элемент `clusters` | Поля clusters.csv; `top_gids` здесь настоящий JSON-массив строк |
| Элемент `top_nodes` | Поля top_nodes.csv с gid-строкой |

`in_degree` и `out_degree` — количества различных наблюдаемых контрагентов; `n_tx_in` и `n_tx_out` — количества транзакций, не количество агрегированных рёбер. `out_in_ratio` = наблюдаемый исходящий оборот / наблюдаемый входящий оборот, `null` при нулевом знаменателе. Наличие числа не делает отношение надёжным для seeds; ограничения отдельно отражаются в `limitations` и правилах.

Аналитик может добавить в `metrics` только реально используемые и документированные показатели, согласовав типы. Поля одного расчёта не расходятся между JSON и CSV. Не включать в JSON все сырые транзакции без потребности обязательного сценария.

`elapsed_ms` в metadata — длительность аналитического запуска от начала чтения исходных файлов до подготовки результата, с точным описанием границы замера в README. Для доказательства лимита Ерасыл дополнительно замеряет процесс снаружи до появления готовых CSV; нельзя вычитать аналитические стадии из заявленного времени.

## 5. Минимальный HTTP API NestJS

| Метод и путь | Вход | Успешный результат |
| :--- | :--- | :--- |
| `POST /api/runs` | Multipart: поля `nodes`, `edges`, `transactions`, каждое — один Parquet | `202`, объект `{run_id, status: "running"}` |
| `GET /api/runs/:run_id` | Серверный идентификатор запуска | `200`, `{run_id, status, elapsed_ms, error}` |
| `GET /api/runs/:run_id/result` | Идентификатор завершённого запуска | `200`, содержимое analysis.json |
| `GET /api/runs/:run_id/exports/:filename` | Идентификатор завершённого запуска и одно из трёх допустимых CSV-имён | `200`, файл для скачивания |

Состояния: `running`, `completed`, `failed`. В статусе `error` равен `null` либо `{code: string, message: string}`. После неудачного запуска нужно показать понятную причину; стектрейс и пути локальной машины остаются в серверной диагностике.

Правила ошибок:

- Неполный комплект или некорректная структура загрузки — `400`.
- Повторный POST, пока выполняется другой расчёт, — `409`; отдельная очередь не нужна.
- Неизвестный run_id или недопустимое имя экспортируемого файла — `404`.
- result/export до состояния completed — `409`; при failed причину можно получить через endpoint статуса.
- Ошибки проверки содержимого Parquet или аналитики после принятия загрузки переводят запуск в failed. Невозможность запустить процесс также отражается как ошибка, не как успешный результат.

При старте нового расчёта frontend явно показывает новый run_id/состояние и не выдаёт старый результат за новый. Состояние выполнения можно опрашивать до терминального статуса; WebSocket не требуется. История запусков и восстановление активного процесса после перезапуска API не являются обязательными функциями; поведение перезапуска описывается честно.

NestJS запускает фиксированный исполняемый Python и модуль через `spawn`/эквивалент с массивом аргументов, без shell-интерполяции. Пользователь не передаёт произвольную команду или файловые пути; входные файлы сохраняются под серверными именами. Для скачивания используется список из трёх разрешённых файлов.

Python выполняется отдельным процессом и не блокирует event loop API. Таймаут и завершение процесса документируются; более длинный технический таймаут не отменяет требование расчёта менее 300 секунд. Для локального сценария достаточно одного API-процесса и одного активного Python-расчёта.

## 6. Проверки на границах компонентов

1. Аналитик проверяет входные схемы и согласованность агрегатов, рассчитывает результат и валидирует свои выходы.
2. Ерасыл перед completed проверяет exit code, наличие всех артефактов, обязательные поля, типы и основные связи CSV/JSON. Валидация не дублирует формулы ролей.
3. Илья отображает поля контракта, различает пустой результат, ошибку и выполнение; не генерирует локально «недостающие» роли или объяснения.
4. Проверка официального датасета сравнивает множество gid с исходными nodes.parquet; проверка «2248 строк» сама по себе недостаточна.
5. Интеграционная проверка выбирает один gid и сверяет его роль, кластер, обе оценки и evidence между CSV, JSON, API и UI; затем повторяет сценарий на изоляте и узле четвёртого шага.
