## Обязательный подход: Test-Driven Development (TDD)

Для каждого нового поведения и исправления ошибки выполняй цикл **Red → Green → Refactor**:

1. **Red:** из требования ТЗ или согласованного контракта выдели небольшой проверяемый сценарий, напиши тест до реализации и запусти его. Убедись, что он падает из-за отсутствующего поведения или воспроизводимого бага, а не из-за сломанного окружения.
2. **Green:** добавь минимальный рабочий код для прохождения теста, не расширяя объём задачи и не подменяя поведение фиктивным успехом.
3. **Refactor:** улучши структуру без изменения внешнего поведения; повторно запусти тесты изменённой части и регрессионные проверки API.

Тестируй наблюдаемое поведение, а не внутренние имена методов. Для API нужны проверки HTTP-контракта, для запуска CLI — управляемые сценарии дочернего процесса и файлов; моки не заменяют отдельный сквозной тест с настоящим Python CLI после готовности аналитики.

До реализации соответствующего сценария добавляй тесты на неверную загрузку, неизвестный запуск, второй активный расчёт, преждевременный доступ к результату, недопустимое имя выгрузки, ошибку запуска/ненулевой exit code Python, отсутствие или повреждение артефактов. Проверяй освобождение слота после ошибки, отсутствие ложного `completed`, изоляцию запусков и сохранение int64/денежных строк. Точные ответы и статусы бери из контракта, не выдумывай их ради теста.

Баг сначала воспроизводи регрессионным тестом. Не ослабляй assertions и не пропускай тесты ради зелёного результата. Если текущая заглушка заменяется реализацией, обновляй её тесты по согласованному контракту. Без фактического запуска честно сообщай, что этап Red или Green не проверен.

Используй существующий тестовый стек; из корня выполни `npm run build:contracts`, затем `npm run test --workspace @money-graph/api`. Перед передачей запускай `npm test`, сборку и проверку типов по README. В отчёте указывай проверенное поведение, команды и фактические результаты Red/Green; не заявляй о прохождении приёмки ТЗ только по мокам.

## Контракт аналитического процесса

После установки Python-пакета из корня репозитория должен работать вызов:
`python -m money_graph --input-dir <directory> --output-dir <directory>`
Входная директория содержит `nodes.parquet`, `edges.parquet`, `transactions.parquet`.
Выходная директория содержит `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv` и внутренний `analysis.json`.
Схемы трёх CSV должны точно совпадать с ТЗ и `docs/CONTRACTS.md`; не переименовывай и не расширяй их самостоятельно.
`analysis.json` используется для связи backend и frontend; это не дополнительная обязательная пользовательская выгрузка.
Его верхний уровень: `metadata`, `nodes`, `edges`, `clusters`, `top_nodes` — точные поля бери из общего контракта.
CLI должен выполнять расчёт и выгрузку без запущенных Next.js и NestJS.
Логи процесса не заменяют выходные файлы; успешный exit code сам по себе не означает корректный результат.

## HTTP API

Реализуй только согласованные методы:

- `POST /api/runs`: multipart-поля `nodes`, `edges`, `transactions`; ответ `202` с `{run_id, status: "running"}`.
- `GET /api/runs/:run_id`: `{run_id, status, elapsed_ms, error}`; статусы `running`, `completed`, `failed`.
- При отсутствии ошибки `error = null`; при ошибке — `{code, message}` с понятной причиной.
- `GET /api/runs/:run_id/result`: возвращает целый проверенный `analysis.json`.
- `GET /api/runs/:run_id/exports/:filename`: отдаёт один из трёх обязательных CSV.
- Для выгрузок разрешены только `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`.
- Одновременно выполняется один расчёт; следующий POST при активном расчёте возвращает `409`.
- Неизвестный `run_id` возвращает `404`; запрос результата или CSV до `completed` возвращает `409`.
- Отсутствующие или некорректные поля загрузки возвращают `400`; остальные детали ошибок сверяй с общим контрактом.

Не добавляй отдельные API поиска, графа, пагинации, уведомлений или пересчёта метрик.
Для заданного объёма frontend получает результат и выполняет поиск и отображение локально.
Согласуй с Ильёй точные поля ответов и ошибки до параллельной реализации.

## Безопасность и надёжность интеграции

- Для каждого расчёта создавай отдельный серверный каталог с раздельными входами и выходами.
- Имена файлов и пути назначает сервер; не используй клиентские пути или исходные имена для построения команд.
- Запускай Python через `spawn` с отдельными аргументами и `shell: false`.
- Обрабатывай ошибку запуска, stdout, stderr, ненулевой exit code и завершение процесса по сигналу.
- Потребляй потоки stdout/stderr без блокировки дочернего процесса и без бесконтрольного накопления в памяти.
- Освобождай слот активного расчёта во всех конечных состояниях, включая ошибки валидации результата.
- Не публикуй частичные артефакты; выставляй `completed` только после проверки всех четырёх файлов.
- Не смешивай результаты разных запусков и не подменяй неудачный запуск ранее успешным результатом.
- Внешний текст ошибки должен помогать исправить проблему; технические подробности сохраняй в локальных логах.
- Не конвертируй идентификаторы int64 в JavaScript `number`: это может незаметно изменить `gid`.
- В JSON все `gid`, `src`, `dst` и элементы `top_gids` — десятичные строки; суммы в KZT — десятичные строки.
- `cluster_id`, `rank` и счётчики — числа; оценки — конечные числа в диапазоне `[0,1]`.
- В CSV идентификаторы сохраняются как точные десятичные целые; не переписывай CSV через Number.
- Если нужно сравнить денежные значения, используй точную десятичную арифметику; не вычисляй аналитику заново в NestJS.
- Проверяй содержимое входов через согласованную валидацию Python, а не только расширение загруженного файла.

## Обязательные приёмочные проверки

Проверяй результаты относительно реально прочитанного `nodes.parquet`, а не встроенного списка ожидаемых узлов.
Для предоставленного набора из ТЗ ожидаются 2 248 уникальных узлов, включая 19 seeds без рёбер.
Эти числа — контроль конкретного датасета, а не ограничение универсального загрузчика или источник предсказаний.
Каждый входной узел должен появиться в `nodes_roles.csv` ровно один раз; лишние и потерянные узлы недопустимы.
Допустимы только роли `consolidator`, `transit`, `distributor`, `terminal`, `coordinator`, `peripheral`.
Не требуй искусственно непустого множества каждой роли: проверяй допустимые значения и покрытие правил по ТЗ.
Все обязательные значения заполнены; оценки конечны и принадлежат `[0,1]`; `evidence` не длиннее 200 символов.
У каждого узла есть существующий кластер; ссылки, размеры кластеров и идентификаторы согласованы между артефактами.
`top_nodes.csv` содержит минимум 20 уникальных узлов, ранжирование по приоритету и обоснования согласно ТЗ.
Проверь точный состав и порядок CSV-колонок по общему контракту и сохранение int64 без потери точности.
Проверь совпадение результатов в CSV и `analysis.json`, который получает интерфейс.
Полный расчёт от исходных Parquet до обязательных CSV должен занимать менее 300 секунд.
Измеряй этот интервал отдельно от установки зависимостей, запуска веб-приложения и загрузки файлов по HTTP.
Записывай реальные длительность, размер входов и окружение; не подменяй измерение оценкой сложности.
Проверь ошибки Python, повреждённые или отсутствующие артефакты, второй параллельный запуск и недопустимое имя выгрузки.
Без реального датасета нельзя объявлять приёмку на данных ТЗ завершённой; моки допустимы только как явно обозначенные dev-данные.
