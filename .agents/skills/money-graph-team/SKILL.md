# Money Graph: командная работа

## Начало новой рабочей задачи

1. До изменения кода или переключения ветки спроси в чате: **«Как тебя зовут?»** Дождись ответа. Если участник уже явно назвал себя в этой задаче, используй этот ответ. Не определяй человека по git user.name, имени компьютера, текущей ветке или сохранённой локальной настройке. В следующих сообщениях той же задачи повторять вопрос не нужно.
2. Найди участника в `team.config.json`: Илья → `ilya-branch-front`; Ерасыл → `yerasyl-branch-back`; Родион → `rodion-branch-analytics`. Неизвестное имя — причина уточнить участника, а не выбрать ближайшую роль.
3. Из корня запусти `node scripts/team.mjs start --name "<полученное имя>"`, затем `node scripts/team.mjs check`. Скрипт переключает на существующую локальную ветку или создаёт tracking-ветку от соответствующей `origin/*`, устанавливает локальную проверку ветки и git hooks.
4. Если ветка отсутствует, сначала проверь `git remote -v`; для origin этого проекта выполни `git fetch origin` и повтори. Не создавай ветку участника от произвольного HEAD и не переназначай существующую ветку.
5. При незакоммиченных изменениях в другой ветке, detached HEAD, ветке в другом worktree или конфликте существующих hooks останови переключение, объясни точный блокер и согласуй сохранение работы. Не выполняй автоматические stash, commit, reset, checkout --, удаление, force или перенос чужих изменений.
6. Подтверди участнику имя, ветку и зону ответственности. Прочитай его промпт из `team.config.json`. Перед изменением API/CLI/выгрузок прочитай `docs/CONTRACTS.md`; для объёма и приёмки — `docs/TEAM_PLAN.md`.

Для дочернего агента в той же рабочей задаче используй подтверждённую родителем личность и текущий checkout. Дочерние агенты не переключают ветки в общем каталоге. Явно порученная владельцем разовая настройка общей структуры выполняется как общая задача, а не приписывается одному из участников; это не исключение для обычной разработки функциональности.

## Фиксированные границы

| Участник | Ветка | Код |
| :--- | :--- | :--- |
| Илья | `ilya-branch-front` | `apps/web/`: Next.js, TypeScript, Cytoscape.js |
| Ерасыл | `yerasyl-branch-back` | `apps/api/`: единственный HTTP API NestJS |
| Родион | `rodion-branch-analytics` | `analytics/`: Python CLI, pandas, PyArrow, NetworkX |

`packages/contracts/` — общие типы и JSON Schema; `docker/`, `compose.yaml`, корневые зависимости, `scripts/`, `.githooks/`, `.github/`, skill и базовые инструкции — общая инфраструктура. Согласовывай изменения общих контрактов с затронутыми участниками; изменение выбранного стека или верхнего уровня структуры требует явного решения владельца проекта. Обычные модули внутри своей зоны создавать можно.

- Python считает метрики, роли, кластеры и приоритеты, создаёт три CSV и `analysis.json`.
- NestJS запускает тот же Python CLI отдельным процессом и отдаёт готовые результаты. В Docker у API есть Node.js и Python; отдельный постоянно работающий Python HTTP-сервис не нужен.
- Next.js отображает результаты. Не добавлять Next Route Handlers/Server Actions для второго API, FastAPI, Spring, БД или брокер сообщений.
- Не переносить код в альтернативные `frontend/`, `backend/`, `services/` или корневой `src/`. Не обходить проверки структуры и ветки.
- `main` — общая интеграционная ветка. Обычную разработку выполнять только в закреплённой ветке; не переключать коллег и не пушить чужие ветки. Владелец разрешил синхронизацию каждые 20 минут по протоколу ниже; это не разрешение на деплой или публикацию данных.
- У каждого человека должен быть отдельный клон или worktree. Одновременное переключение веток в одной общей папке меняет checkout для всех процессов.

## Синхронизация каждые 20 минут

Перед commit/push/merge или настройкой расписания полностью прочитай [docs/TEAM_SYNC.md](../../../docs/TEAM_SYNC.md). Он определяет разрешённые ветки, проверки, остановку при конфликте и готовый промпт для коллег. Сохраняй только собственную проверенную работу, получай origin, объединяй свою удалённую ветку и две ветки коллег **в свою ветку**, проверяй результат и пушь только её. Нельзя публиковать сломанное состояние ради расписания. При конфликте, чужих изменениях в затрагиваемых файлах или падающих проверках останови автоматический цикл и сообщи блокер.

Для просьбы о повторяющейся синхронизации настрой реальный 20-минутный heartbeat текущей задачи через доступный инструмент расписаний, без дубликатов. Skill сам не запускает таймер. В продолжениях одной задачи используй уже подтверждённое имя, не спрашивай его каждые 20 минут; если checkout сменился, не переключай его автоматически. Дочерние агенты не запускают собственный цикл.

## Готовность результата

Для backend обязателен TDD (Red → Green → Refactor), включая регрессионный тест до исправления ошибки; конкретные проверки и порядок работы — в `docs/prompts/erasyl-backend.md`. Для frontend обязательна палитра `docs/design/xi-palette.svg`; перед изменением оформления прочитай раздел палитры в `docs/prompts/ilya-frontend.md`. Не заменяй её собственной цветовой системой.

Главное правило — полностью выполнить обязательное ТЗ, обеспечить объяснимость, локальную воспроизводимость и полный пересчёт менее 300 секунд. Приёмка и веса 25/25/25/15/10 сохранены в `docs/TEAM_PLAN.md`. Дополнительные функции обсуждать после обязательной приёмки.

Точность gid и денежных сумм, все узлы включая изоляты, ограничения depth=4 и неполных входящих потоков обязательны. Не выдавать каркас, synthetic fixture, эвристический score или заглушку за готовый анализ.

Перед передачей выполнить `npm run team:check`, `npm run check:structure` и релевантные сборки/тесты своей части из README. При общей интеграции проверить Docker Compose. Отчитаться о фактических результатах и непроверенных требованиях; не объявлять весь продукт готовым только по успешной сборке.

Skill и hooks помогают соблюдать процесс, но не являются контролем доступа. Не утверждать, что текстовая инструкция технически запрещает любое изменение или автоматически защищает удалённую ветку GitHub.
