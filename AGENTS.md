# Инструкции проекта Money Graph

## Сначала участник и ветка

Перед началом новой задачи прочитай `.agents/skills/money-graph-team/SKILL.md` и спроси в чате: **«Как тебя зовут?»** Дождись ответа до изменений кода и Git. Если человек уже явно назвал себя в текущей задаче, не спрашивай повторно. Не угадывай личность по git config или текущей ветке.

Далее выполни `node scripts/team.mjs start --name "<имя>"` и `node scripts/team.mjs check`. Илья → `ilya-branch-front`; Ерасыл → `yerasyl-branch-back`; Родион → `rodion-branch-analytics`. Скрипт не переносит незакоммиченные изменения между ветками и не создаёт ветку от случайного HEAD. При блокере следуй skill, не используй force/reset/автоматический stash.

Эта процедура относится к участникам, а не к дочерним агентам одной подтверждённой задачи: они наследуют личность и не переключают общий checkout. Разовая явно порученная настройка общего каркаса является общей задачей. `main` служит интеграции; обычная разработка идёт в закреплённых ветках.

Структура зафиксирована: `apps/web`, `apps/api`, `analytics`, `packages/contracts`. Изменение стека или этих границ требует решения владельца проекта. Запускай `npm run check:structure`; не отключай проверки, чтобы обойти ограничение. Общая инфраструктура описана в README и skill.

## Главное правило

Полностью выполнить обязательные требования исходного ТЗ, обеспечить корректность, объяснимость, производительность и воспроизводимость. Не добавлять функции ради демонстрации технологий. Сначала закрыть обязательную приёмку; дополнительные функции обсуждать с пользователем. Не объявлять задачу завершённой при непроверенных обязательных пунктах.

## Зафиксированные решения пользователя

- Стек: Next.js + TypeScript + Cytoscape.js; NestJS + TypeScript — единственный HTTP API; Python CLI + pandas + PyArrow + NetworkX — пакетная аналитика.
- Ерасыл: backend, интеграция Python CLI, запуск, приёмочные проверки, инструкция установки.
- Илья: frontend, граф, пользовательский сценарий, схема и демонстрация.
- Родион: аналитик; данные, метрики, роли, кластеризация, приоритеты, объяснения и методология.
- Python — единственный источник вычислений и экспортов. NestJS и frontend не дублируют аналитические правила.
- Базовый объём не включает FastAPI, Spring, внешнюю БД, брокер сообщений, облако, обязательный LLM или обучение модели.
- Ориентир разработки — 5 часов из ТЗ. Это план, а не подтверждение наличия данных или завершённой реализации.

## Условия качества

- Сохранять все узлы из `nodes.parquet`, включая изоляты; не строить перечень клиентов только по рёбрам.
- `depth=4` и отсутствие исходящих переводов не доказывают, что средства остались на счёте. Неполные входящие потоки, особенно seeds, не позволяют вычислить полный баланс.
- Роли и назначения кластеров — гипотезы для проверки; `role_score` без ground truth не является калиброванной вероятностью.
- Не выдумывать атрибуты клиентов, данные, метрики, результаты тестов или значения порогов, якобы полученные из отсутствующего датасета. Не хардкодить списки «правильных» gid.
- Сохранять int64 идентификаторы без потери точности; в JSON передавать их строками. Не суммировать деньги с потерей точности и не учитывать перевод дважды.
- Три обязательных CSV имеют фиксированные схемы. Полный расчёт от исходных Parquet до CSV должен занимать менее 300 секунд на целевом датасете; подтверждать фактическим измерением.
- Отделять синтетические тестовые данные от результатов реального датасета. При отсутствии данных выполнять независимую работу и явно отмечать непроверенную приёмку.
- Зависимости фиксировать, ресурсы интерфейса хранить локально. CLI должен работать без запущенных NestJS и Next.js.
- В README должны быть фактические команды, критерии ролей и пороги, выходные форматы, ограничения и описание масштабирования до ~1 млн узлов. Будущие команды не выдавать за работающие.
